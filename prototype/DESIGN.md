## Problem-first product direction, November 2026

This section supersedes the prototype layout below. The user could not tell what to implement from the code-first screen. The walkthrough, dense interface, and all-monospace typography did not solve that problem.

The job is to understand and repair one visible behavior in a small simulated settlement. Before exposing the editable module, show the problem, the data model, a function contract, explained input/output examples, and the acceptance rules. The primary action is **Start coding**. A useful problem brief must remain available beside the editor during work. World inspection and actual route playback remain first-class views, not decorative backgrounds.

Keep at most two major panes. Use a single quiet header, a compact mission indicator, and one primary action. Remove the duplicate chapter strip, repeated mission summaries, decorative status metadata, permanent dialogue cards, and redundant editor hints. Put optional audio, lighting, and demo controls behind restrained controls rather than competing with the task. Prefer a short problem-first arrival over another compulsory cinematic tour.

Use locally hosted Manrope for UI text, with 16px body copy and a comfortable 1.65 line height. Use JetBrains Mono only for code, signatures, IDs, and datasets. Keep Monaco at 15px or larger. Headings use the UI family, 26–36px where useful, with fewer all-caps labels. The user's latest request replaces the previous all-monospace requirement.

The world is a grounded island assembled from original procedural hex tiles. Borrow continuous terrain, negative space, and modest height variation from [Dorfromantik](https://store.steampowered.com/app/1455840/Dorfromantik/). Borrow teal water and warm, readable building silhouettes from [Townscaper](https://store.steampowered.com/app/1291340/Townscaper/). Their actual screenshots were reopened and inspected for this revision. Do not copy their assets or reproduce their building density. One landmark per graph station, most tiles empty grass, a few trees, and a visibly broken bridge. Terrain adjacency never creates a working corridor.

The palette uses deep forest surfaces, warm off-white reading panes, sage accents, muted teal water, and restrained apricot for the primary action. The scene is open and warm, the coding surface remains dark for contrast. Avoid a third pane or grids of metadata cards. Inspect the actual render before extending the direction.

This release slice makes the first mission coherent and reliable. It also authors ten distinct follow-up designs, explicitly marked planned rather than pretending to be playable. No accounts, billing, analytics, streaks, or generated level feed are added.

## Art direction

The proposed identity is Aster. This is a working name, not a brand decision.

Use dark plum space, warm ivory text, faded copper controls, and sage success states. Avoid an enterprise dashboard or glowing hacker terminal.

The user selected IBM Plex Mono for the whole interface, including titles, dialogue, code, and telemetry. Serif typography is removed. Local font files avoid runtime font-service dependencies.

Use a 72-pixel header, a compact 38-pixel chapter strip, and a world/editor split. The editor is about 430 pixels wide on a laptop.

The world contains original procedural geometry. It must look like a physical place, with layered platforms, a greenhouse, cargo, and a small drone.

The world offers dusk and day lighting for comparison. The interaction stays identical, so the player can judge atmosphere separately.

## Data and state

The mission uses nodes, safe edges, and one blocked edge. The graph shown to player code contains safe connections only.

The attempt phase is one of ready, executing, animating, failed, or complete. A generation number invalidates stale asynchronous results after reset.

The runner returns a bounded list of node IDs or a diagnostic. Mission validation determines the traversable prefix and the first failure. The world animates that result.

## Scope

One playable level, a real TypeScript editor, isolated execution after compilation, replay, hints, procedural sound, and a clearly marked preview of the next chapter.

The prototype does not prove a curriculum, a production sandbox, cross-device performance, or long-term retention.
